# Data schemas

Every CSV this artifact reads or writes is specified here. `analysis/io.py`
validates against these schemas and **rejects a file with missing or extra
columns**, on purpose: a silently renamed column becomes a silently wrong figure,
and a figure that plots a different quantity from the one its axis names is worse
than no figure.

## Conventions that apply to every file

| Convention | Meaning |
|---|---|
| Empty cell | **Not measured.** Never zero, never imputed, never carried over from a neighbouring row. Empty becomes `NaN` in pandas and travels through the analysis as a missing value, ending as a red `\PLACEHOLDER` in the manuscript. |
| `0` | A measured zero. Distinct from empty. |
| Leading `#` lines | Comments, skipped on read. Synthetic files declare themselves here (see below). |
| Time | Unix seconds, float. `t_rel_s` is seconds since the start of that run. |
| Latency | Milliseconds, unless a column name says otherwise. |
| CPU | Millicores. 1000 millicores = one core fully busy. |
| Rates | Requests per second. |
| Scenario labels | `S1`…`S9` exactly (see below). Any other label is a schema error. |

### Synthetic-data marker

Files produced by `data/make_example_data.py` begin with:

```
# SYNTHETIC EXAMPLE DATA - NOT FOR PUBLICATION. Generated by data/make_example_data.py ...
```

`analysis/io.data_is_synthetic()` treats a directory as synthetic if **either**
the resolved path contains `example` **or** any CSV in it carries that marker.
Both checks exist so that renaming a directory or stripping a header is not
enough to defeat the guard. Figures built from synthetic data are watermarked;
LaTeX macros derived from it are wrapped in `\SYNTHVAL` and typeset in red.

## `scenarios.csv`

One row per (scenario, run, throughput window). Written by
`experiments/run_closedloop_scenario.sh` via `experiments/merge_scenario.py`.

| Column | Type | Description |
|---|---|---|
| `scenario` | `S1`…`S9` | Configuration under test. |
| `environment` | `local` \| `eks` | Where the run happened. These are **not** pooled by the analysis. |
| `run` | integer | Repetition index, 1-based. |
| `throughput_rps` | float | Completed requests per second over the window named in `throughput_window`. |
| `throughput_window` | `steady` \| `full` | Which window `throughput_rps` covers. See the note below — this column exists specifically to remove an ambiguity in the manuscript. |
| `latency_mean_ms` | float | Mean response time over the window. |
| `latency_p50_ms` | float | Median. |
| `latency_p90_ms` | float | 90th percentile. |
| `latency_p95_ms` | float | 95th percentile. |
| `latency_p99_ms` | float | 99th percentile. |
| `latency_stdev_ms` | float | Sample standard deviation over the per-request samples in the window. k6 does not report this, so `merge_scenario.py` computes it from `k6_raw.csv`; it is empty when the per-request samples were not retained. |
| `cpu_app_millicores` | float | Mean CPU of the application container over the window. |
| `cpu_sidecar_millicores` | float | Mean CPU of the Envoy sidecar over the window. |
| `cpu_ingress_millicores` | float | Mean CPU of the ingress controller over the window. |
| `cpu_limit_millicores` | float | The pod's configured CPU limit. Not a measurement — a constraint. A stack that reaches it is being throttled, and every latency number from that run means something different. |

### `throughput_window`: why both rows exist

A closed-loop run has a ramp-up, a steady phase and a ramp-down. Dividing the
same CPU figure by throughput measured over the *steady phase* and over the
*whole profile* gives amortised CPU costs that routinely differ by 20–40%. The
manuscript does not say which it used. Emitting one row per window makes the
choice explicit and lets `analysis/amortized_cpu.py` report both and their ratio.

## `latency_samples.csv`

Per-request latencies, for the density figure. Written by
`experiments/merge_scenario.py` from the k6 CSV output.

| Column | Type | Description |
|---|---|---|
| `scenario` | `S1`…`S9` | |
| `environment` | `local` \| `eks` | |
| `run` | integer | Repetition this sample came from. |
| `latency_ms` | float | One request's end-to-end response time. |

Notes:

* Samples come from the **steady window only**. Including the ramp would blend
  two different operating points into one distribution.
* Long runs are downsampled by an evenly spaced stride (`PSAO_MAX_LATENCY_SAMPLES`,
  default 200 000), never by truncation, so the retained sample still spans the
  whole window.
* `analysis/stats_tests.py` treats these as the `per_request_samples` unit and
  states explicitly that p-values computed over them describe distributions, not
  the treatment.

## `openloop_ramp.csv`

One row per ramp step. Written by `experiments/run_openloop_ramp.sh` via
`experiments/merge_ramp.py`. This is the input to the elbow fit.

| Column | Type | Description |
|---|---|---|
| `scenario` | `S1`…`S9` | |
| `environment` | `local` \| `eks` | |
| `target_rps` | float | The arrival rate k6 was told to offer. The **independent variable**. |
| `achieved_rps` | float | Requests actually issued per second during the step. Below saturation this equals `target_rps`; above it, the generator falls behind. |
| `latency_mean_ms` | float | Mean response time during the step. |
| `latency_p99_ms` | float | 99th percentile during the step. |
| `cpu_app_millicores` | float | Mean application CPU **during that step's time window**, from 1 s samples. |
| `cpu_sidecar_millicores` | float | Mean sidecar CPU during the step. |
| `eventloop_lag_p99_ms` | float | See the important caveat below. |

Notes:

* **Repeated sweeps append rows.** Running the ramp three times gives three rows
  per `target_rps`. `fig_elbow.py` aggregates them into a mean with a 95% CI;
  with a single sweep no error bar is drawn, rather than a zero-width one.
* `elbow_fit.py` fits only steps where `achieved_rps >= 0.95 * target_rps`.
  Beyond that the nominal λ is not the offered λ, and fitting those points fits
  the load generator rather than the service. Excluded steps are reported.
* **`eventloop_lag_p99_ms` is the mean of the per-scrape p99 values observed
  during the step.** It is *not* a p99 over the step. Averaging quantiles does
  not produce a quantile. The column is named for the underlying gauge; this
  note is the correction, and nothing in the analysis treats it as a true p99.

## `controller_trace.csv`

One row per control interval. Written continuously (flushed per row) by
`controller/psao_controller.py`.

| Column | Type | Description |
|---|---|---|
| `t_unix` | float | Wall-clock time of the observation. |
| `t_rel_s` | float | Seconds since the first observation of this run. |
| `lambda_rps` | float | Observed arrival rate. |
| `eventloop_lag_p99_ms` | float | Event-loop delay p99 over the last scrape window. |
| `mu_eff_rps` | float | Effective service rate in force: either the configured fixed value or the online estimate `λ / utilization`, EWMA-smoothed. |
| `rho` | float | `lambda_rps / mu_eff_rps`. Empty when `mu_eff` is not yet established. |
| `latency_mean_ms` | float | Observed mean response time. |
| `mode` | `app` \| `sidecar` | Where verification is running **after** this interval's decision. |
| `decision` | `hold` \| `offload` \| `revert` | What the controller did. Only `offload` and `revert` are transitions. |
| `actuation_latency_ms` | float | Milliseconds from the decision to the policy being *observed in effect*. Empty on `hold` rows and whenever no confirmation method is configured. See below. |
| `trigger_reason` | string | Machine-readable reason. See the grammar below. |

### `actuation_latency_ms`: what it measures

Defined by `actuation.confirm` in `controller/config.yaml`:

| `confirm` | The clock stops when… | Caveat |
|---|---|---|
| `probe` | a request carrying a deliberately invalid token is rejected by the sidecar | Data-plane truth. **This is the defensible number to publish.** |
| `resource` | the Kubernetes API server returns the object | Control-plane write latency only. Envoy may not be reconfigured yet, so this **understates** actuation latency, often by seconds. |
| `none` | — | Column left empty. |

Under `--dry-run` the recorded value is the genuine wall time of the local
(no-op) code path, typically well under a millisecond. It is **not** an estimate
of cluster actuation latency and must never be published as one. Dry-run rows
are identifiable from the run log and from the run metadata.

### `trigger_reason` grammar

| Form | Meaning |
|---|---|
| `below_trigger(rho=…)` | Holding in `app` mode; no trigger term fired. |
| `above_revert(rho=…)` | Holding in `sidecar` mode; not all revert conditions met. |
| `rho=…>0.7` / `cpu=…m>700m` / `predicted_latency=…ms>15ms` | The terms that fired, joined by `\|`. |
| `suppressed:<offload\|revert>:<consecutive(n/N)\|dwell(Xs_remaining)>:<terms>` | A would-be transition blocked by hysteresis or by the minimum dwell time. Counted as a suppressed flap. |
| `actuation_failed:<decision>:<detail>` | The transition was attempted and failed; the mode did **not** change. |
| `no_rho(missing:…)` | ρ could not be formed; the named observations were missing. |

Suppressed flaps are recoverable from the trace alone (`decision == hold` and
`trigger_reason` starting `suppressed:`), so the count in the paper is
reproducible from the shipped data without reading the controller's log.

## `microbench.csv`

Written by `bench/jwt-path-microbench.js`. One row per
(algorithm, stage, payload size).

| Column | Type | Description |
|---|---|---|
| `algorithm` | `HS256` \| `RS256` | |
| `stage` | see below | Which part of the validation path was timed. |
| `payload_kb` | float | Target size of the **encoded** JWT payload segment, in kilobytes. |
| `iterations` | integer | Timed iterations **after** the warm-up fraction was discarded. |
| `mean_us` | float | Mean time per operation, microseconds. |
| `p50_us` | float | Median (nearest-rank). |
| `p99_us` | float | 99th percentile (nearest-rank). |

### Stages

| Stage | What is timed |
|---|---|
| `full_verify` | `jsonwebtoken.verify()`: everything, exactly as the service does it. |
| `decode_only` | Split on `.`, base64url-decode header and payload, `JSON.parse`. **No signature check.** The parsing floor. |
| `primitive_preparsed` | `node:crypto` performing the signature check over the real JWT signing input, with the key already parsed into a `KeyObject` outside the loop. |
| `primitive_raw` | The same primitive over a pre-allocated buffer of identical byte length. No JWT structure, no string→bytes conversion. The absolute cryptographic floor. |

Derived quantities used by `fig_validation_path.py`:

```
signing_input_assembly = primitive_preparsed - primitive_raw
library_overhead       = full_verify - (decode_only + primitive_preparsed)
```

`library_overhead` **may be negative**. The stages are timed in separate loops,
and an isolated loop is specialised more aggressively by the JIT than the same
work inside the full call. When it is negative the figure draws it as a hatched
bar below the axis labelled "over-attribution". It is never clamped: the sign
bounds how much of the decomposition is an artefact of measuring the stages
apart, which is information a reader is entitled to.

The timer overhead (two `hrtime.bigint()` calls per sample, order 50–100 ns) is
measured and printed by the benchmark but **is not subtracted** from any reported
figure.

## `keypath_mechanism.csv`

One row per **process invocation**, written by `bench/keypath-mechanism.js` and
driven by `experiments/run_keypath_mechanism.sh`. Aggregated by
`analysis/keypath_stats.py`.

| Column | Type | Description |
|---|---|---|
| `environment` | string | `host`, or the container image tag (`node:18.20.8-alpine`). Rows from different environments must never be pooled: the same condition differs by 20x between them. `analysis/keypath_stats.py` groups on this column and defaults it to `host` for files written before it existed. |
| `condition` | string | Which stage was measured. See the table below. |
| `invocation` | int | Round number. The runner cycles through every condition inside each round, so rows sharing an `invocation` saw the same machine state and are legitimately paired. |
| `n` | int | Calls timed in this invocation, after warmup. |
| `mean_us` | float | Mean over those calls. Reported but not used as the headline: the distribution is right-skewed by preemption, so the median is the stabler summary. |
| `median_us` | float | **The per-invocation figure the analysis aggregates.** |
| `p90_us`, `p99_us` | float | Tail within the invocation. |
| `min_us`, `max_us` | float | Extremes within the invocation. |
| `stddev_us` | float | Sample standard deviation within the invocation. |
| `timer_overhead_us` | float | Median cost of the `process.hrtime.bigint()` pair itself, measured in this same process. Reported, **never subtracted**. |
| `node_version` | string | e.g. `v26.6.0`. Recorded by the measuring process itself, **not** by the host. `run_metadata.json`'s `node_version` is `node --version` on the host (`common.sh:559`) and does not describe a containerised service — `service-a` is `FROM node:18-alpine` and runs v18.20.8. |
| `openssl_version` | string | e.g. `3.6.3`. The finding lives in OpenSSL's error path, so its version is part of the measurement rather than background to it. |
| `platform` | string | e.g. `darwin/arm64`. Present so host and container rows stay distinguishable when runs are concatenated. |

### Conditions

| `condition` | What it times |
|---|---|
| `jwt_hs_string` | `jwt.verify()`, HS256, **string** secret — what an ordinary service does. |
| `jwt_hs_preparsed` | `jwt.verify()`, HS256, `KeyObject` secret. |
| `jwt_hs_string_safe` | As `jwt_hs_string`, against the safe-patched library (`bench/keypath-patch.js`). |
| `jwt_rs_pem_string` | `jwt.verify()`, RS256, PEM **string** — here the `createPublicKey()` probe succeeds. |
| `jwt_rs_preparsed` | `jwt.verify()`, RS256, `KeyObject`. |
| `probe_throws` | `createPublicKey(<hmac secret>)`, which throws and is discarded. |
| `probe_succeeds` | `createPublicKey(<rsa pem>)`, which does not throw. |
| `create_secret_key` | `createSecretKey(Buffer.from(secret))` — the conversion itself. |
| `hmac_string` | `createHmac('sha256', <string>)` through `digest()`. |
| `hmac_keyobject` | `createHmac('sha256', <KeyObject>)` through `digest()`. |
| `decode_only` | Structural base64url + JSON decode, no signature check. |
| `timer_overhead` | Empty body: the floor this clock resolves. |

**Why one condition per process.** Measuring every condition in one process lets
the first condition's compiled code, inline caches and heap layout follow the
later ones, and reports one sample as if it were a population. Each row here
comes from a separate `node` process, so the interval
`analysis/keypath_stats.py` reports covers between-process variation. Rows from
a single invocation must not be quoted as a result on their own.

## `security_check.csv`

Written by `bench/keypath-security-check.js`. One row per (library variant,
test case). Not a measurement — an assertion log, kept because the timing result
for the patched library is only meaningful if the patch is sound.

| Column | Type | Description |
|---|---|---|
| `variant` | `stock` \| `naive` \| `safe` | Which build of `jsonwebtoken` was exercised. |
| `case` | string | Test case name. |
| `expected` | `accept` \| `reject` | What that variant is **documented** to do. `naive` is expected to `accept` the confusion attack: that is the regression being demonstrated. |
| `observed` | `accept` \| `reject` | What it did. |
| `detail` | string | `ok` or `MISMATCH`, plus the rejection message where there was one. Commas are stripped from library messages so the field stays single-column. |

The script exits non-zero if any variant departs from its documented behaviour —
including if `naive` ever stopped being vulnerable, which would mean the
demonstration had gone stale against a newer `jsonwebtoken`.

## `survey/data/hand_adjudication.csv`

One row per call site read and classified **by hand**. Written by the author,
not by a script: the automated classifier's output is in `callsites.csv`, and
this file records where a human overrode or confirmed it.

| Column | Type | Description |
|---|---|---|
| `round` | string | **Which question was being asked.** See below. Two rounds live in this file and must not be pooled. |
| `repo` | string | `owner/name`. |
| `path_kind` | `application` \| `benchmark` \| `demo` | What kind of code the file is. A library benchmark or a vulnerability demonstration is not evidence about deployed practice. |
| `arg2_at_matched_callsite` | string | The second argument as written at the call site. |
| `resolves_to` | string | What that argument resolves to within the file, or a note that it does not. |
| `verdict` | string | Round-specific; see below. |
| `note` | string | Why the verdict was reached. |
| `git_blob_sha1` | hex \| empty | Git blob hash of the bytes read. Comparable to the `sha` field GitHub's contents API returns for that path. **May be empty — see below.** |
| `sha256` | hex \| empty | SHA-256 of the same bytes. |
| `repo_head_commit` | hex \| empty | Repository HEAD at manifest time, not at fetch time. The weakest column; the blob hash is the authoritative pin. |
| `adjudicator` | string | Who classified it. Currently `author` for every row: there was no second rater, and the paper states this as a limitation. |

### The `round` column

The two rounds asked **different questions of different corpora**, and their
`verdict` vocabularies are therefore disjoint. Pooling them produces a number
that answers neither question.

| `round` | Corpus | Question | `verdict` values |
|---|---|---|---|
| `counter_search_2026-09-17` | Files co-occurring `jsonwebtoken` with the pre-parsing API, fetched deliberately | *Does this file really pass a pre-parsed key to `verify()`?* | `genuine`, `false_positive`, `unresolved` |
| `sample_rematch_2026-09-18` | The residue of the random-ish sample that the first matcher did not classify | *What key form does this call site use?* | `not_keyobject` |

`analysis/make_keypath_macros.py` filters on this column. `\Adjudicated*`
macros are computed from the **counter-search** rows only; `\Rematch*` macros
from the rematch rows only. Both are correct for what they name.

The filter removes no genuine site: every rematch row is `not_keyobject`, so the
count of genuine pre-parsed call sites is **7 across 6 projects whether the
rounds are filtered or pooled**. This was checked rather than assumed.

### Why three rows have blank hashes

`git_blob_sha1`, `sha256` and `repo_head_commit` were added after the
counter-search round had already been adjudicated, and were backfilled from
`corpus_manifest.csv` by matching on repository.

**That match is ambiguous for a repository that contributed more than one file**,
because this file records `repo` but no `path`. Three counter-search rows are in
that position — two repositories contributed two files each. Rather than attach a
hash that might belong to the other file, those cells are left empty.

Empty here therefore means *not determinable*, consistent with the convention at
the top of this document: it is never a zero, and never a guess. The affected
rows can be resolved by hand against `corpus_manifest.csv`, which does record
paths. Rows written after the schema change carry all three columns.

## Combining runs

Each runner writes into its own `data/runs/<ISO timestamp>-<label>/`. To analyse
several runs together, concatenate their CSVs into one directory, keeping a
single header:

```sh
mkdir -p data/measured
for f in scenarios latency_samples openloop_ramp; do
  awk 'FNR==1 && NR!=1 && /^scenario,/ {next} !/^#/' \
      data/runs/*/"$f".csv > data/measured/"$f".csv
done
make analysis DATA=data/measured
make figures  DATA=data/measured
```

Each run directory also holds a `run_metadata.json` recording the cluster
version, Istio version, node instance types, running image digests and the
artifact's git commit. Anything that could not be determined on the host is
recorded as `null` and listed under `unavailable` — never guessed.
