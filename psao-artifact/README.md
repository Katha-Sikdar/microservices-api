# PSAO reproducibility artifact

Code that **produces** the measurements behind *predictive security-aware
offloading* (PSAO) of JWT verification in a Kubernetes microservice under layered
Zero Trust enforcement.

The paper it supports measures event-loop saturation in a Node.js service as
Edge TLS, Istio mTLS and application-level JWT validation are layered on, models
the service as a single-server queue, and proposes relocating token verification
to the Envoy sidecar *before* the saturation point is reached. It was desk
rejected for two reasons: the policy existed only as pseudocode, and several
reported quantities were derived rather than measured. This repository closes
both gaps.

---

## The one rule

**This repository ships no measurements.**

Every number in a figure or a generated LaTeX macro comes from a CSV you
produced by running an experiment here. The only numeric data in the repository
is clearly-labelled synthetic example data, generated by
`data/make_example_data.py`, whose sole purpose is to exercise the pipeline on a
laptop with no cluster.

Three guards enforce this:

1. **Watermark.** Any figure built from a data path containing `example`, or
   from files carrying the synthetic header marker, is stamped diagonally with
   `SYNTHETIC EXAMPLE DATA — NOT FOR PUBLICATION`. `figures/style.finalize()` is
   the only save path, and it refuses to write a figure whose provenance it
   cannot evaluate.
2. **Red placeholders.** `paper/generated_macros.tex` defines one macro per
   number the manuscript cites. A quantity the data does not contain is emitted
   as `\PLACEHOLDER{key}`, which typesets in red as `[MISSING: key]`. Nothing in
   this artifact turns a missing measurement into a plausible one.
3. **`\SYNTHVAL`.** When the analysis runs on synthetic data, every macro value
   is wrapped so it typesets in red with a dagger. Example data can be taken all
   the way to a compiled PDF and still cannot be mistaken for a result.

If you find a number in this repository that is not (a) a configuration value,
(b) a policy threshold, or (c) synthetic example data that says so, that is a
bug worth reporting.

## Quick start (no cluster required)

```sh
cd psao-artifact
make setup          # creates .venv, installs Python + Node dependencies
make example-data   # generates SYNTHETIC data in data/example/
make analysis       # fits, tests, and paper/generated_macros.tex
make figures        # seven vector PDFs in figures/output/ — all watermarked
```

Then look at `analysis/output/summary.txt`. Everything in it is derived from
fabricated input; the point of the exercise is that the pipeline runs and that
the guards fire.

To run against real measurements, point `DATA` at a run directory:

```sh
make analysis DATA=data/runs/2026-09-06T14-22-31Z-S5-run1
make figures  DATA=data/runs/2026-09-06T14-22-31Z-S5-run1
```

## What each piece is for

### `instrumentation/eventloop-metrics.js`

Express middleware exporting Prometheus metrics on a **separate port** (default
`9464`) — separate because the application port is the thing being saturated, and
scraping it would make the scrape compete with the load under test.

* Event-loop delay from `perf_hooks.monitorEventLoopDelay` at **1 ms
  resolution**, as p50/p90/p99/max/mean gauges. The default 10 ms resolution
  cannot distinguish a healthy loop from an elbow forming at single-digit
  milliseconds; every quantile would read the same.
* A request-duration histogram with ~1 ms bucket edges through the 3–15 ms band
  where the scenarios live, plus a coarse tail that still resolves post-elbow
  queueing. Prometheus' defaults place only three edges in that whole band.
* A **separate histogram for the synchronous verification call alone**, via
  `timeVerify(algorithm, fn)`. This is what resolves the paper's open
  discrepancy between the fitted service rate and the CPU-derived one: with it,
  the CPU-derived rate can be attributed to a specific synchronous section
  instead of inferred from a pod-level average.
* `psao_eventloop_utilization`, the controller's online `mu_eff` input.

### `bench/jwt-path-microbench.js`

**Precision: state the crypto share as "roughly 5-6% of `jwt.verify()`", not
"5.1%".** The single-run figure was 5.1%, but its numerator is
`primitive_preparsed`, a sub-2 us quantity where the timer floor dominates.
Three repeat passes on a quiet host measured 1.484 / 1.440 / 1.381 us at 0.5 kB
— a 7.2% spread — so the third significant figure is not real and should not be
quoted. Two stages are worse and should carry the same caveat:
`HS256 decode_only` at 0.5 kB (0.895 / 1.011 / 0.893, 12.6% spread) and
`HS256 primitive_preparsed` at 2 kB (1.904 / 2.134 / 1.985, 11.4%).

The conclusion is unaffected. Single digits against a ~91% library-overhead
residual is the finding; 5.1% versus 5.6% is not. Run
`make microbench REPEAT=3` and read `microbench.spread.txt` before quoting any
stage under about 3 us.

By contrast every `full_verify` figure — the denominator, and the number the
decomposition is a share *of* — reproduced within 2.7% across three passes, and
within 1.1% for the 0.5 kB cases the paper uses.


Decomposes `jwt.verify()` into `full_verify`, `decode_only`,
`primitive_preparsed` and `primitive_raw` (see `docs/DATA_SCHEMA.md`), for HS256
and RS256 at 0.5/2/4 kB payloads. The question it settles: **how much of
"signature verification" is actually parsing?** If parsing dominates, then moving
verification to the sidecar does not remove that cost — the sidecar parses too —
and PSAO's claim has to be about *where* work happens rather than about work
disappearing.

```sh
node bench/jwt-path-microbench.js --iterations 1000000 --out data/runs/bench/microbench.csv
make microbench ITERATIONS=200000     # equivalent
```

No cluster, no HTTP, no `cluster` module.

### `controller/psao_controller.py`

The paper's title contribution, running. Once per control interval it polls
Prometheus, maintains `mu_eff`, forms `rho = lambda / mu_eff`, and evaluates

```
offload  if  rho > rho_trigger  or  cpu > cpu_trigger
         or  predicted_latency(rho, mu_eff) > sla
```

where predicted latency is the **M/D/1** waiting time. Using the *predicted*
rather than the observed latency is the "predictive" part: it is the only way to
actuate before the elbow rather than after it.

`mu_eff` has two modes. `fixed` takes a value from config — and the config ships
that value as `null`, so the controller **refuses to start** in fixed mode until
you fill it in from your own elbow fit. `online` estimates it continuously as
`lambda / utilization` from measured event-loop occupancy, EWMA-smoothed and
guarded at both inputs.

On trigger it applies an Istio `RequestAuthentication` **and** a matching
`AuthorizationPolicy` through the Kubernetes API. Both, always: a
`RequestAuthentication` alone rejects *invalid* tokens but lets *untokened*
requests straight through to the application, so relocating verification with
only that object would turn an authenticated endpoint into an open one. See the
header comment in `controller/policy_template.yaml`.

It measures **actuation latency** per transition: wall time from the decision to
the policy being observed in effect. With `actuation.confirm: probe` that means
an actual request carrying an invalid token is rejected by the sidecar — data
plane, not an API-server acknowledgement. A policy that takes longer to take
effect than the elbow takes to form is not a solution, and this is the number
that says which it is.

Hysteresis, and why: a single threshold on a noisy signal chatters, and every
crossing is an Istio configuration push that moves a production service's
enforcement point. Three independent brakes — a revert band strictly below the
trigger, a consecutive-sample requirement, and a minimum dwell time — each
failing differently. **Every suppressed flap is logged and lands in the trace**
with `trigger_reason` starting `suppressed:`, so the flap count is reproducible
from the shipped data.

```sh
# offline: replay a recorded trace through the policy, no cluster touched
make controller-dry-run

# live
python controller/psao_controller.py --config controller/config.yaml
```

Ctrl-C reverts to the application-layer configuration before exiting. Leaving a
cluster with verification pinned in the sidecar after the controller has died is
a silent change to the enforcement point, so reverting is the default and
`--no-revert-on-exit` is an explicit opt-out.

### `experiments/`

| Script | What it does |
|---|---|
| `run_openloop_ramp.sh` | k6 in **open-loop constant-arrival-rate** mode, stepping to 400 rps in 20 rps steps of 30 s, with `capture_pod_metrics.sh` sampling pod CPU at 1 s alongside. **This is the run that measures pod CPU *at* the elbow** instead of deriving it. |
| `run_closedloop_scenario.sh` | One closed-loop scenario repetition (the manuscript's original 100-VU profile), producing `scenarios.csv` and `latency_samples.csv`. |
| `run_controller_experiment.sh` | Runs PSAO against the cluster while a ramp crosses the trigger and then falls back through the revert band, capturing `controller_trace.csv`. |
| `capture_pod_metrics.sh` | 1 s CPU sampling. |

**Why not `kubectl top`.** metrics-server aggregates over ~15 s and refreshes on
its own schedule, so polling it every second returns the same stale number about
fifteen times — and 15 s is longer than a whole ramp step, so no `kubectl top`
sample belongs to a single arrival rate. That is precisely why the manuscript can
only report CPU derived from a scenario average. `capture_pod_metrics.sh` instead
differences the kernel's own `cpu.stat` `usage_usec` counter inside each
container (default), or queries cAdvisor through Prometheus.

**Why open loop.** Every measurement in the manuscript came from a closed-loop
test: 100 VUs each sleeping 1 s. A closed-loop generator slows down when the
service slows down, so offered load is not an independent variable and there is
no λ to put on the x-axis of a queueing model. That is the methodological hole
behind the missing elbow figure.

All runners write into `data/runs/<ISO timestamp>-<label>/` with a
`run_metadata.json` capturing cluster version, Istio version, node instance
types, running image digests and the artifact's git commit. Anything that could
not be determined is recorded as `null` and listed under `unavailable`.

### `analysis/`

* **`elbow_fit.py`** — fits **both** M/M/1 (`W = 1/(μ−λ)`) and M/D/1
  (`W = 1/μ + ρ/(2μ(1−ρ))`) by least squares, reporting fitted μ, RMSE and MAPE
  for each. The manuscript reports no goodness of fit at all and fits only
  M/M/1; M/D/1 is the more defensible model for a fixed-cost operation and
  predicts exactly half the queueing delay at the same ρ. Each model is also
  fitted with a free additive offset, because measured HTTP latency includes
  ingress and network time that no single-server model accounts for — and the
  gap between the two variants **is** the fitted-versus-CPU-derived discrepancy
  the paper could not explain. The elbow is the maximum-curvature point of the
  fitted curve on normalised axes; if that lands on the edge of the measured
  range it is reported as `UNRESOLVED` rather than extrapolated. CPU at the
  elbow is interpolated between the two bracketing *measured* steps, and says so.
* **`stats_tests.py`** — Welch's t-test, Mann-Whitney U, Cohen's d with pooled
  SD, and BCa bootstrap CIs on the median difference (10 000 resamples), with
  Bonferroni correction across the comparisons against S1. Results are reported
  in **two labelled families**: `run_means` (n = repetitions; the unit that
  supports a claim about the configuration) and `per_request_samples` (n =
  requests; describes distributions, and its p-values are explicitly *not*
  evidence about the treatment). The manuscript does not say which it used, and
  the two differ by orders of magnitude.
* **`amortized_cpu.py`** — amortised CPU per request computed **both** ways,
  normalised by steady-state throughput and by full-profile throughput, plus the
  percentage by which the choice changes the published number.
* **`run_all.py`** — runs everything, writes `analysis.json` and
  `summary.txt`, and emits `paper/generated_macros.tex`.

## Cluster preconditions that will bite you

Four configuration facts are not derivable from the manifests, and each one
produced a broken or silently meaningless measurement path in this testbed at
least once. They are recorded per-run under `cluster_configuration_notes` in
every `run_metadata.json`, so a run directory carries its own preconditions.

**1. `ingress-nginx` must be in the mesh.** The namespace needs
`istio-injection=enabled` and the controller pod must come up `2/2`
(`controller` + `istio-proxy`):

```sh
kubectl label namespace ingress-nginx istio-injection=enabled --overwrite
kubectl -n ingress-nginx rollout restart deploy/ingress-nginx-controller
```

The paper's Section 3.1 specifies an injected NGINX pod; an un-injected
controller is cluster drift, not an alternative configuration. Un-injected, edge
traffic never enters the mesh and the mTLS leg being measured does not exist.

**2. The injected controller crash-loops without an outbound exclusion.** Its
Kubernetes API client hangs behind the sidecar. `holdApplicationUntilProxyStarts`
alone does **not** fix it. What works is excluding the API server VIP from
interception, on the controller's pod template:

```yaml
annotations:
  traffic.sidecar.istio.io/excludeOutboundIPRanges: "10.96.0.1/32"
```

*This does not affect what the experiment measures.* `10.96.0.1/32` is the
Kubernetes API server VIP and nothing else. Every measured data-plane hop —
client to ingress, and ingress to `service-a` — is still intercepted by Envoy
and still carries mTLS. The exclusion removes only the controller's own
watch/list calls from the proxy, and those are on no measured path. Confirm the
VIP on your own cluster rather than copying the literal; it is
`kubectl -n default get svc kubernetes -o jsonpath='{.spec.clusterIP}'`.

**3. The Ingress needs `service-upstream`.** By default `ingress-nginx`
load-balances to endpoint **pod IPs** (`10.x.x.x:3000`), bypassing the Service
VIP. Istio has no listener for a bare pod IP on the application port, so the
sidecar's passthrough sends **plaintext** into `service-a`'s `STRICT` mTLS
inbound port and the connection is reset. NGINX logs `upstream prematurely
closed connection` and returns **502** for every request:

```sh
kubectl -n default annotate ingress my-ingress \
  nginx.ingress.kubernetes.io/service-upstream=true --overwrite
```

Targeting the ClusterIP instead lets the sidecar match the service VIP, apply
the `DestinationRule`, and originate mTLS. This also does not change what is
measured: it changes which address NGINX dials, not what is on the wire.

**4. Re-mint the tokens before a measurement session.** `tokens/` is an input,
not a measurement, but it expires — and an expired pool does not fail loudly.
`service-a` answers **403** to every request, k6 records those 403s as fast
responses, and the ramp produces a smooth, plausible, entirely meaningless
latency curve for an error path.

```sh
node experiments/mint_tokens.js --count 64 --ttl 24h
```

### The controller's rate windows must match the scrape interval

`controller/config.yaml` originally asked Prometheus for `rate(...[30s])`. Both
jobs in this testbed scrape every **15 s**, so a 30 s window has exactly two
samples — the bare minimum — and returns nothing at all the moment one scrape is
late. Measured here:

```
sum(rate(container_cpu_usage_seconds_total{...}[30s])) * 1000  ->  NO DATA
sum(rate(container_cpu_usage_seconds_total{...}[1m]))  * 1000  ->  98.6
```

An intermittently-absent `cpu_millicores` means `cpu_trigger_millicores` can
never be relied on to fire, and the controller would run an entire experiment on
the ρ signal alone while appearing to weigh CPU as well. The windows are now
`1m`, following the usual "at least 4× the scrape interval" guidance.

**The trade-off, stated:** a 1 m window smooths harder, so a rising load is seen
later. During the S3 ramp, with k6 offering 250 rps, the 1 m window reported 206
rps and a 30 s window reported 234 — the lag is real and visible. The decision
logic still needs only ~6 s of agreement (`poll_interval_s: 2` ×
`consecutive_trigger_samples: 3`), but the signal it agrees about lags by up to
~30 s. **Actuation latency measured against this configuration includes that
observation lag and must be reported as such, not as pure control-loop latency.**

A second hazard in the same query: `pod=~"service-a-.*"` also matches pods from
previous rollouts whose cAdvisor series have not yet gone stale. At a 5 m window
this cluster summed three pods, two of them dead, and reported 329 millicores.
The 1 m window is short enough that a pod deleted over a minute ago contributes
no rate — but if you lengthen it, scope the query to the live pod explicitly.

### Failure modes that produce a complete-looking run

Three of these have already happened here. All three produced a run directory
that looked finished. They are listed because the shape is the point: the
dangerous failures in this artifact are not crashes, they are runs that complete
and are wrong.

**An expired token pool.** Every request 403s, k6 records the 403s as fast
responses, and the ramp draws a smooth latency curve for an error path.
*Caught by:* the pre-flight check below. *Prevented by:* `make tokens`.

**A dead CPU sampler.** `capture_pod_metrics.sh` runs under `set -euo
pipefail`, and its optional event-loop-lag scrape was an unguarded pipeline
called once per iteration *before* the sampling loop. One failed scrape of
`/metrics` returned non-zero and killed the sampler on its first iteration. The
ramp then ran its full ten minutes and wrote a normal `openloop_ramp.csv` with
an empty CPU column — and an empty CPU column is indistinguishable from the
legitimate "no cluster was available" case. *Fixed by:* guarding the optional
scrape, letting a failed iteration warn-and-continue, and making
`run_openloop_ramp.sh` **fail the run** when the sampler was started but wrote
no samples. A ramp without CPU cannot produce CPU-at-the-elbow, which is the
derived number this experiment exists to replace.

**A backup that cannot be restored.** The mesh-posture backup was taken with
`kubectl get -o yaml` and kept verbatim, on the reasoning that server-populated
fields were harmless. `resourceVersion` is not harmless: it carries optimistic
concurrency, so re-applying it fails with *"the object has been modified"* for
any object that still exists — which is every object the teardown *patched*
rather than deleted. The S1 restore failed on the Ingress for exactly this
reason, leaving mTLS restored but edge TLS off. *Fixed by:* stripping
`resourceVersion`, `uid`, `generation`, `status` and the stale
`last-applied-configuration` from the backup (the raw dump is kept alongside in
`raw/`), and restoring with **server-side apply**, which reconciles from desired
state alone and so both re-creates a deleted object and updates a surviving one.
The pre-teardown dry run now goes through that same path — a dry run that
exercises a mechanism the restore does not use proves nothing.

That last failure also produced its own misleading success: with no `spec.tls`
for the host, ingress-nginx still answers HTTPS **200** using its own default
self-signed certificate. The restore therefore checks that the Ingress names its
TLS secret, and does not treat a 200 as evidence.

### The pre-flight check

Because 502 and 403 both produce full-looking runs, every runner sends one
request through the exact path it is about to hammer, before it creates a run
directory or generates any load, and **aborts** unless the status matches
(`psao::verify_ingress` in `experiments/common.sh`). A ramp is ten minutes and
its output is indistinguishable from a good one without reading status codes, so
the check is worth the one request it costs. Override the expected status with
`PSAO_EXPECT_STATUS` only when you are certain the code you are accepting is the
one the *scenario* is supposed to produce, not the one the cluster happens to be
producing.

Verify by hand with:

```sh
curl -k -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $(head -n1 tokens/hs256.token)" \
  https://localhost/products     # expect 200
```

## Running the scenarios

The cluster manifests live in the sibling `microservices-api/` testbed. Bring the
cluster into the configuration for a scenario **first**, verify the rollout
finished, and only then run the load generator — `run_closedloop_scenario.sh`
deliberately does not apply manifests, because an automated "apply then measure"
makes it far too easy to measure a configuration that had not finished rolling
out.

### Two drivers do the cluster transitions

`run_openloop_ramp.sh` still never touches the cluster — an automated "apply
then measure" makes it far too easy to measure a configuration that had not
finished rolling out. But S1, S3, S8 and S9 are *not* the configuration the
cluster rests in, and doing those transitions by hand is how a run ends up
mislabelled. Two drivers do them, wait for each to land, and verify it:

```sh
experiments/run_scenario_ramp.sh    --scenario S1   # mesh posture + PSAO_AUTH_MODE
experiments/run_scenario_ramp.sh    --scenario S3
experiments/run_scenario_service.sh --scenario S8   # swaps the pod behind the Service
experiments/run_scenario_service.sh --scenario S9
```

`run_scenario_ramp.sh` handles the layers *below* the application: it sets
`PSAO_AUTH_MODE`, waits for the rollout, tears the mesh posture down for S1, and
**restores and re-verifies it afterwards** — exiting non-zero and saying so
loudly if the restore cannot be proven, because every later run would otherwise
be measured, and labelled, in the wrong posture.

`run_scenario_service.sh` swaps which implementation sits behind the `service-a`
Service. All three Deployments (`service-a-deployment`,
`service-a-s8-deployment`, `service-a-s9-deployment`) carry `app=service-a`, so
the Service, the Ingress, the edge TLS and the mTLS leg are byte-identical
across S5, S8 and S9 — that is what puts them on one axis. It scales the others
to zero first and then **refuses to ramp unless exactly one endpoint backs the
Service**, checking endpoints rather than pods: a terminating pod lingers in the
pod list after leaving the endpoint set, and two live endpoints would mean the
ramp silently measured a blend of two implementations.

The S8/S9 image is built from the artifact root (the services load
`../instrumentation/eventloop-metrics.js`), on the same `node:18-alpine` base
and the same dependency ranges as `service-a`:

```sh
docker build -f scenarios/deploy/Dockerfile -t psao-scenarios:psao-2 .
kubectl apply -f scenarios/deploy/s8-deployment.yaml
kubectl apply -f scenarios/deploy/s9-deployment.yaml   # both start at replicas: 0
```

**S9's CPU limit is not a detail.** S5 and S8 are single-threaded and cannot
exceed about one core whatever the pod allows. S9 forks workers, so on an
unlimited pod it would simply take more CPU and report more throughput — which
answers a question nobody asked. The S9 Deployment is therefore capped at
`1000m`, the same budget S5 is confined to by being single-threaded, and
`WORKERS` is pinned rather than left to `availableParallelism()`, which reads the
*node's* core count rather than the pod's quota and would fork ten workers into a
one-core cgroup, turning the run into a study of CFS throttling. A throughput
figure for S9 without its CPU budget attached is not interpretable; if you want
S9 given N cores, raise both together and say which budget the number came from.

### One image, one digest, across every scenario

S1-S3 are defined without application-level JWT validation and S4-S9 with it.
The original testbed switched between the two by commenting the JWT block out of
`service-a/index.js` and rebuilding — so S1-S3 and S4-S5 were measured on
**different images**, and any difference between those builds sits inside the
very comparison the elbow figure makes.

`service-a` now selects the handler at startup instead:

```sh
kubectl -n default set env deploy/service-a-deployment PSAO_AUTH_MODE=none  # S1..S3
kubectl -n default set env deploy/service-a-deployment PSAO_AUTH_MODE=jwt   # S4..S9
kubectl -n default rollout status deploy/service-a-deployment
```

The mode is resolved once, at startup, and registers one of two handlers; it is
not a per-request branch on a path being measured at millisecond resolution.
`run_metadata.json` records the image digest, so a reader can confirm that two
scenarios really were the same build.

### Mesh posture, and why a 200 does not prove it

S1 is the only scenario measured with the mesh posture torn down. Use the script
rather than ad-hoc `kubectl delete`, because it backs up what it removes and
because **the restore is verified**:

```sh
experiments/set_mesh_posture.sh --posture s1      # tear down, after backing up
experiments/set_mesh_posture.sh --posture full    # restore, then VERIFY
experiments/set_mesh_posture.sh --verify          # verify only, change nothing
```

A 200 from `https://localhost/products` is **not** proof that mTLS came back — a
200 is also exactly what an *absent* STRICT policy produces, with the request
travelling in plaintext. So `--posture full` checks three things, and exits
non-zero if any of them fails:

1. a namespace-wide `PeerAuthentication` with `mtls.mode: STRICT` exists;
2. a `DestinationRule` carries `trafficPolicy.tls.mode: ISTIO_MUTUAL`;
3. **paired controls on the same address** — an *in-mesh* client (a pod with a
   sidecar) must **get a response**, and an *out-of-mesh* client (namespace
   `psao-probe`, explicitly un-injected) must be **refused**.

Only the third tests behaviour rather than declared intent, and the positive
half of it is not optional. A refusal on its own is equally consistent with
nothing listening at that address at all — the first version of this check
probed `.items[0]` of the pod list, which during a rollout is the **old,
terminating** pod, got `Connection refused` from a dying process, and passed.
Pinning both probes to the same Service ClusterIP is what makes the refusal mean
"mTLS rejected this" rather than "there was nothing there".

Both probes target the **ClusterIP**, not a pod IP: Istio has no listener for a
bare pod IP on the application port, so even an in-mesh client is passed through
in plaintext there and would be refused too — making the positive control fail
for a reason that has nothing to do with posture.

If the restore cannot be verified, abort the remaining runs; do not continue on
a 200.

Every `run_metadata.json` carries a `mesh_posture` block with the posture
observed at run start and the timestamped `change_events` log
(`data/runs/posture_events.jsonl`), so it is visible from any run directory
which posture its numbers were measured in.

**What S1 is not.** The teardown removes the mTLS policy and the edge TLS; it
does **not** remove the sidecars. In S1 a request still traverses the ingress
Envoy and the `service-a` Envoy, in plaintext. S3 − S1 therefore isolates the
cost of mTLS *crypto and policy*, not the cost of the proxy hop, which is
present in both. That is arguably the cleaner decomposition — but it is not the
same claim as "S1 is a mesh-free baseline", and it must not be written up as one.

| Scenario | Setup |
|---|---|
| S1 | Plain HTTP; no `mtls-policy.yaml`, no TLS on the ingress; run with `--no-auth`. |
| S2 | Edge TLS on the ingress; `--no-auth`. |
| S3 | S2 plus `mtls-policy.yaml` (`STRICT`) and `destination-rule.yaml`. |
| S4 | Plain HTTP plus application JWT (HS256); pass a token. |
| S5 | S3 plus application JWT (HS256). |
| S6 | S5 with the service and tokens switched to RS256. |
| S7 | S5 with the controller's offload policy applied (or let the controller apply it). |
| S8 | S5 with `scenarios/s8-token-cache.js` as the service. |
| S9 | S5 with `scenarios/s9-cluster-mode.js` as the service. |

Tokens are minted **outside** k6 by `experiments/mint_tokens.js`, and passed in
by file:

```sh
node experiments/mint_tokens.js --count 64 --ttl 24h   # writes both files below
export PSAO_TOKEN_FILE=./tokens/hs256.token       # single token
export PSAO_TOKEN_POOL=./tokens/pool.txt          # one token per line
```

The runners resolve `--token-file` / `--token-pool` to absolute paths before
handing them to k6. k6's `open()` resolves a relative path against the directory
of the *script* that calls it — `experiments/k6/lib/` — not against your shell's
cwd, so `--token-pool tokens/pool.txt` would otherwise abort the run at init.

Use a **pool** for S8. A single token makes every request after the first a cache
hit, which is a dishonest best case for the cache.

## Security notes worth reading before citing S7 or S8

**The S9 CPU limit determines what S9 means.** See the Deployment comment: S5
and S8 are single-threaded and confined to about one core, so S9 is capped at
`1000m` to ask whether forking helps *within the same CPU budget*. Uncapped on a
10-core node it would simply take more CPU and report more throughput. A
throughput number for S9 without its CPU budget attached is not interpretable.

**S8's cache TTL is a security parameter.** Caching a verification result
weakens revocation: between a token being revoked and its cache entry expiring,
the service accepts a token it should reject. Entry lifetime is
`min(configured TTL, remaining exp)`, so a cached entry can never outlive its
token — but that bounds the damage, it does not remove the gap. With the default
30 s TTL, S8 buys its throughput with a 30-second revocation window. PSAO does
not. If S8's numbers appear in the paper, so must that sentence.

**The offload makes the application trust a header, and that was a real bypass.**
PSAO only works if verification *moves*. With `forwardOriginalToken` alone the
handler still ran `jwt.verify()` on every request, so verification was
duplicated, no CPU left the event loop, and the central claim was unmeasurable.
The fix is `outputPayloadToHeader`: Istio writes the verified claims into
`x-psao-jwt-payload`, and `service-a` reads them instead of re-checking the
signature.

That makes the service's security depend on a client being unable to set that
header. Istio overwrites it — **but only while a `RequestAuthentication`
exists**, and the controller applies one only transiently, above the trigger. In
every other state, which is most of the time and all of S1/S3/S5/S8/S9, nothing
sanitised it. Measured on this cluster, with no offload policy applied and **no
`Authorization` header at all**:

```sh
curl -k -H "x-psao-jwt-payload: eyJzdWIiOiAiYXR0YWNrZXIifQ" https://localhost/products
# -> 200, with the protected payload
```

A complete authentication bypass. `controller/strip-untrusted-payload-header.yaml`
closes it: an always-on `EnvoyFilter` that removes any client-supplied copy of
the header on entry to the pod, before any JWT filter runs. It is matched on the
connection manager with `INSERT_FIRST`, **not** on `jwt_authn` — a patch matched
on `jwt_authn` would not be inserted at all in precisely the state that needs it,
because in that state there is no `jwt_authn` filter. Apply it once and leave it
applied:

```sh
kubectl apply -f controller/strip-untrusted-payload-header.yaml
experiments/verify_offload_safety.sh      # regression test, run after any change
```

Measured after the fix — forged header alone is refused in both states (401 with
no policy, 403 with the policy's `AuthorizationPolicy`), a valid token still
returns 200, and a valid token accompanied by a deliberately malformed forged
header also returns 200, which proves the client's value never reached the
handler (it would have failed closed with 500).

**`PeerAuthentication` STRICT is load-bearing for this, not just for
confidentiality.** STRICT is what stops a client reaching port 3000 without
traversing that filter chain. Drop mTLS to `PERMISSIVE`, or expose the pod
directly, and the bypass reopens even with the EnvoyFilter applied. This is the
concrete reason `set_mesh_posture.sh --verify` refuses to accept a 200 as
evidence that mTLS came back.

**The actuation confirmation must be two-sided.** `actuation.confirm: probe`
originally checked only that a *malformed* token was rejected by the sidecar. A
misconfigured JWKS makes Envoy reject **every** token with exactly that same
401 — so a uniformly broken endpoint confirmed as a successful offload, and the
trace would have recorded an actuation latency for an outage. That was not
hypothetical: the shipped `jwks_uri` pointed at `https://psao.example/...`, a
domain that does not resolve. The probe now also requires that a *valid* token
still returns 2xx (`actuation.probe_token_file`).

**S7 (offload) moves the trust boundary.** RS256 is the deployable path: the
sidecar fetches public keys and no secret leaves the issuer. HS256 requires
handing the shared secret to every sidecar as an inline `oct` JWKS — Envoy will
verify it, but the secret is then distributed far more widely than the single
application it was issued for. That is a real weakening, and it is why S6 (RS256)
exists as a scenario at all.

## What is committed under `data/runs/`, and what `k6_raw.csv.gz` is for

`data/runs/INDEX.md` is the map: every run directory, its scenario, whether it is
canonical, and one line on why each non-canonical run was set aside. Read it
before opening any run directory.

Each ramp directory ships **`k6_raw.csv.gz`**, the per-request sample dump,
compressed roughly 51x (3824 MB raw across the set, 75 MB gzipped). **It is
archival.** `experiments/merge_ramp.py` consumes the *uncompressed* `k6_raw.csv`
during a run, to derive each step's time window from real request timestamps
rather than an assumed schedule; nothing reads it after the run finishes.
`make analysis` and `make figures` both work from `openloop_ramp.csv`, which is
already merged and committed alongside it.

So a reviewer who never gunzips anything can still reproduce every figure and
every macro. The gzip is there so the merge step itself can be audited, not
because the pipeline depends on it. If you do want to re-run the merge:

```sh
gunzip -k data/runs/<run dir>/k6_raw.csv.gz
PSAO_RUN_DIR=data/runs/<run dir> python3 experiments/merge_ramp.py
```

## The machine these measurements came from

Every number in `data/runs/` was produced on this host. It is a laptop, and that
matters: the load generator, the ingress, the sidecars and the service all share
the same cores, which is why the trustworthy measurement window ends at about
1000 rps (see `data/runs/PROBE-2026-09-13-find-saturation/README.md`).

| | |
|---|---|
| CPU | Apple M4, 10 cores (10 physical / 10 logical) |
| RAM | 16 GB |
| OS | macOS 26.5.2 (build 25F84) |
| Docker Desktop | 4.45.0 (203075), engine 28.3.3 |
| Kubernetes | v1.32.2 (client and server) |
| Cluster shape | single node `docker-desktop`, 10 CPU, 7.65 GiB allocatable |
| Container runtime | `docker://28.3.3` |
| Istio | 1.28.0 (`docker.io/istio/pilot:1.28.0`), `demo` profile, revision `default` |
| ingress-nginx | controller `v1.14.0`, **injected into the mesh** |
| Node.js | v26.6.0 |
| k6 | v2.2.0 (go1.26.5, darwin/arm64) |

**Pod resources:** `service-a` (S1, S3, S5) and the S8 deployment run with **no
CPU request and no limit** — being single-threaded confines them to about one
core anyway. The S9 deployment is the exception, capped at
`requests = limits = 1000m` with `WORKERS=4`, deliberately, so that forking is
measured against the same budget the single-threaded scenarios are confined to.
An S9 throughput number quoted without that budget is not interpretable.

**The cluster is not isolated.** k6 runs on the same host as the cluster it is
driving. Above ~1000 rps the generator, the ingress and the control plane contend
for the same 10 cores; during one controller run the Kubernetes API server itself
became unreachable. Treat anything above that as unusable, and do not compare
these absolute numbers against a run on dedicated hardware — compare shapes.

The bash scripts are written for **bash 3.2** (the macOS system bash): no
associative arrays.

Two version notes worth knowing before you debug something that looks broken:

* **k6 v2 no longer copies the process environment into `__ENV`.** Only variables
  passed with `-e` are visible to a script. The runners build that list
  explicitly (`psao::k6_env` in `experiments/common.sh`); if you invoke k6 by
  hand, export is not enough.
* **`prom-client` 15.x prints a deprecation notice** pointing at
  `@prometheus-io/client`. The artifact stays on `prom-client`, which is what the
  instrumentation is specified against. One sharp edge: a cluster worker's IPC
  responder is installed by the `AggregatorRegistry` *constructor*, not by
  `setRegistries()`, so S9 constructs one in each worker. Without it
  `clusterMetrics()` times out and `/metrics` silently serves nothing — see the
  comment in `scenarios/s9-cluster-mode.js`.
